ExpansionHunter Genotype-Quality Model — Training & Evaluation Pipeline

Orchestrated end-to-end by train_model.sh. The genotype-quality (GQ) model corrects ExpansionHunter (EH) allele-size calls: for each allele it predicts a length-correction factor (LCF) and direction probabilities (pOk / pTooShort / pTooLong).

1. Step-by-step breakdown

  • Stage 1 — Data ingestion

    dataset.py (with eh_json.py, features.py)

    Downloads from GCS and assembles the labeled training tables. Three remote sources per sample are fetched — the EH JSON, the tool-independent truth-genotypes TSV and the DipCall high-confidence BED; the old precomputed *.for_comparison.*.alleles.tsv.gz table is no longer downloaded or read (its contents are reconstructed downstream from these two). Downloads are idempotent and freshness-aware: a local copy is re-used only while it is current — _check_freshness re-downloads (overwrites) any file whose bucket object is newer by last-modified time or whose md5 has changed, and the per-combo parquet is rebuilt whenever a source it derives from is newer than it.

    Inputs

    • gs://tandem-repeat-explorer/tool_genotype_quality/expansion_hunter_v2.1/<sample label>/json/*.json.gz (dataset.EH_RESULTS_ROOT) — raw optimized-streaming EH output on the 5.65M-locus TRExplorer v2.1 catalog, one run per sample label: the training combos HG002_10x / HG002_20x / HG002 (31x) and CHM1_CHM13 (46x), the promoted samples and the held-out samples. Carries the genotype calls, confidence intervals, read-support counts, and per-allele quality metrics. Why: this is the sole source of the model's input features and the eh call being corrected — every feature the model reads comes from the JSON, never from a precomputed TSV, so features are computed identically across samples/coverages/branches.
    • gs://tandem-repeat-explorer/tool_genotype_quality/truth_genotypes_v2.1/ (dataset.TRUTH_GENOTYPES_ROOT) — the tool-independent truth genotypes on the same catalog (Short/Long allele repeat counts, NumRepeatsInReference, motif, per-allele purity) built from the dipcall/long-read-assembly pipeline; one file per sample (truth doesn't depend on short-read coverage). Why: supplies the training target — the true allele size each call is scored against (t = log(eh) − log(true)) — and, being tied to no EH run, cannot go stale relative to one. It is filtered at load to EH's catalog loci (primary contigs + variant, non-hom-ref, per convert_truth_set_to_variant_catalogs.py) so it lines up with the loci the JSON actually contains.
    • The sample's DipCall high-confidence BED (gs://str-truth-set-v2/dipcall_pipeline/…/<sample>.dip.bed.gz, listed in high_confidence_beds.tsv) — truth loci not wholly inside one confident region are dropped, so every truth allele the model trains or is scored on comes from a region the assembly resolved.
    • 50 PROMOTED_HELDOUT_SAMPLES per-sample parquets (54 training sources with the 4 combos), built on demand via heldout.build_sample from the same three GCS sources and symlinked into the training pool. Why: HG002+CHM1_CHM13 alone leave the large-allele tail overfit to two genomes; these add ancestry/sex diversity at large sizes.

    Role

    • eh_json.extract_rows flattens each JSON into one row per allele. A no-call locus (EH emitted ./.) now yields rows with a null eh so the report can later count those truth alleles as "No Call"; these rows are dropped before training.
    • _load_truth_from_genotypes_tsv filters the truth catalog to EH's catalog loci (primary contigs + variant, non-hom-ref), then _join_truth left-joins it on (locus_id, allele_rank); _assert_catalog_agreement refuses to build (raises) when more than 2% of the filtered truth loci are missing from the JSON overall, or more than 15% in any truth-size bin, and otherwise prints a summary of the gap.
    • label_and_filter drops chrM/unknown-contig, negative-control, missing/non-positive-eh-or-true (including the no-call rows), and missing-motif rows, then features.add_labels computes the targets and routes each allele to a genotyping regime.
    • assemble_branch splits rows by genotyping_branch (QuickGenotype fast-path vs full-genotyper fallback) and concatenates all combos + promoted samples per branch, keeping a seeded uniform sample of up to 100,000 representative rows per source per genotyping regime (the only rows used for early stopping, calibration and the report's CV test rows) plus a training-only quota top-up of rare motif-type × called-size cells and recording each row's person in an individual column (HG002's three coverages are one person) for the person-level hold-out in Stage 2.

    Outputs

    • data/parquet/quick.parquet, data/parquet/full.parquet — labeled per-allele rows (features + t, dir_code, genotyping_regime), split by genotyper branch.
    • Per-combo parquets under data/real_quick/ (e.g. HG002_31x.parquet) — the pre-filter join, kept with locus_id/true/no-call rows so Stage 3's accuracy-by-size can reconstruct the tool-vs-truth comparison table.

    Note — what is not a Stage-1 (training) input: HG002 exome (3x) is not ingested here and never trains the model; it was a Stage-3 report evaluation dataset (a legacy hand-built parquet) and is currently disabled because that parquet is unavailable. CHM1_CHM13 is a training combo (46x). The 81 fully-held-out HPRC samples never enter the training pool.

  • Stage 2 — Train + export

    train.py (with model.py)

    Inputs

    • data/parquet/quick.parquet, data/parquet/full.parquet — the labeled per-allele training rows from Stage 1. Why: these are the only fit inputs — each of the 3 genotyping-regime experts reads its branch's parquet, restricted to its own regime's rows, to fit both heads.

    Freshness guard: both train.py and report.py call dataset.assert_parquets_up_to_date before reading the pool, and exit with a rebuild message if a parquet is missing or older than any upstream JSON/TSV it derives from — so a stale parquet can never be silently trained/reported on.

    Role

    • For each regime (quick, full_spanning, full_nonspanning): hold out the isotonic-calibration rows (seeded): 5 whole people plus HG002's and CHM1_CHM13's rows on one autosome (so calibration sees 10x/20x/46x coverage; HG002 and CHM1_CHM13 train on all their other chromosomes), representative rows only; train on every chromosome, and cap training rows with a seeded quota sample spread evenly over (homopolymer or not) × called allele size.
    • train_direction fits a 3-class classifier + per-class isotonic calibration. train_q_median fits a quantile (median) regressor on t = log(eh) − log(true) using only the rows the pOk < 0.5 gate fires on, judged out of fold by two 500-iteration direction heads fit on opposite halves of the training people, since the LCF is only ever applied to those calls. Both heads are fit to a fixed number of iterations per regime (train.ITERATIONS_BY_REGIME: direction 150 / 3,000 / 3,000, q-median 300 / 6,000 / 6,000), chosen from learning curves: with people held out, early stopping never stops, because more trees keep learning catalog loci that new people share. Quick was cut by hand to 150 for runtime, since its calls are ~93% of the alleles scored (HG002 chr22, every catalog locus) and its curve is nearly flat.
    • serialize_genotyping_regime exports trees/baseline/calibrators to the C++-compatible schema; verify_genotyping_regime re-implements inference from that serialized dict and asserts it reproduces sklearn's predictions.

    Outputs

    • model/genotype_quality_model_from_HG002_and_CHM1_CHM13.<date>.json.gz — gzipped JSON (format_version: 2): per-regime q-median trees + direction trees/calibrators + the feature_names contract. This is the exact file the ExpansionHunter C++ compiles in.
  • Stage 3 — Evaluate + report

    report.py (with metrics.py, accuracy_by_size.py, gen_datasets.py)

    Inputs

    • data/parquet/{quick,full}.parquet — the same training pool. Why: the deployed model is fit on all data and has no held-out set of its own, so honest accuracy is measured by re-fitting each regime out-of-fold under 5-fold chromosome-clean CV on this pool.
    • the exported model/*.json.gz (via --model). Why: it is applied unchanged (no re-fit) to compute LCF/pOk for the accuracy-by-size panels and the held-out section; it also labels the report header.
    • per-combo / per-sample parquets (from Stage 1, and Stage 4 for held-out). Why: accuracy_by_size.categorize_parquet rebuilds the str-truth-set "for_comparison" tool-vs-truth table directly from these — EH calls from the JSON-derived eh, truth from the joined true/num_repeats_in_reference, and "No Call" from the no-call rows — so no precomputed comparison TSV is needed.

    Role

    1. 3a. Homopolymer CV pass (--homopolymer-cv, run first): 5-fold chromosome-clean OOF on 1 bp-motif loci only → results_homopolymer.json, dir_oof_homopolymer.npz.
    2. 3b. Main CV + render: identical OOF on non-homopolymer rows; metrics.py scores q-head accuracy, direction log-loss/AUC/calibration, and the gated MAE (apply LCF only where pOk < 0.5); permutation importance + add-one ablation; renders the PNGs and report/model_report.html.
      Dataset regeneration (default-on): before rendering the dataset sections, report.py calls gen_datasets.generate for every dataset (held-out HPRC, HG002 genome) to refresh its eval/stacked artifacts from the locally-built parquets (no download), and drops any artifact recorded for a different model than --model. Pass --skip-heldout-samples to opt out; a dataset whose parquets haven't been built is skipped.

    Outputs

    • report/results.json, report/dir_oof.npz, the PNG charts, and the final report/model_report.html.
  • Stage 4 — External validationoptional · RUN_HELDOUT_SAMPLES=1

    Builds the 81 truly held-out sample parquets so Stage 3 can score them (the model is applied unchanged — the realistic "train on some samples, deploy on new samples" test). About 0.7 GB of gzipped JSON per sample (about 57 GB for all 81), downloaded one sample at a time and deleted after its parquet is built; off by default.

    1. 4a. heldout.py --build-only
      Input: GCS EH JSON + truth-genotypes TSV + DipCall high-confidence BED for the 81 held-out samples. Why: same three sources / same extract-join-label pipeline (including the confident-region filter) as Stage 1, so the held-out parquets carry identical features (and no-call rows) — a prerequisite for applying the frozen model to them.
      Output: data_eval_43/real_43/<SAMPLE>.parquet × 81.
    2. 4b. Fold into the report
      Once the parquets exist, the ordinary Stage-3 report.py run regenerates the held-out artifacts (report/eval_heldout_hprc.json, report/stacked_heldout_hprc.json) and renders the "held-out HPRC" section by default — no separate gen_datasets.py invocation is needed.
  • Stage 5 — New-vs-previous comparisonpost-hoc · stdout only · non-fatal

    compare_models.py (with heldout.py, gen_datasets.py)

    Applies the freshly-exported model and a previous model to the same held-out HPRC parquets and prints per-regime metric deltas + an overall verdict — the "should we ship the new one?" check. Both models are applied unchanged (no re-fit) to identical rows (same per-sample allele cap + seed as the report's held-out section, so the new model's numbers match it). Runs at the end of every train_model.sh; never fails the pipeline.

    Inputs

    • the new model (--new-model = Stage 2's export) and a previous model (--prev-model): defaults to whichever model is deployed in the local ExpansionHunter-bw2 checkout (ehunter/data/genotype_quality_model_*.json.gz), falling back to the most recent other model/*.json.gz in this repo.
    • the 81 held-out HPRC per-sample parquets from Stage 4 (data_eval_43/real_43/<SAMPLE>.parquet). Why: in neither model's training pool, so applying both to them is a fair generalization comparison.

    Role

    • Reuses heldout.run_eval for each model on the same rows, then scores each genotyping regime separately for homopolymer and non-homopolymer alleles. A group is won only when the per-sample paired difference in gated MAE has a bootstrap 95% interval (2000 resamples over samples) that excludes 0; the verdict is NEW / PREVIOUS / MIXED / NO CLEAR DIFFERENCE. Gate-decision accuracy (pOk<0.5), argmax direction accuracy, median |err| and the net-helped count are printed as context, not counted, and the gated MAE is also shown without the ten fast-path diagnosis samples.
    • Scope, printed with the result: only loci whose truth differs from the reference, and one row per emitted quality-metric entry (a missed heterozygous allele is not counted).
    • When the two models declare different feature_names contracts it reports the difference and builds each model's own feature matrix. Self-skips (prints a note, exit 0) if the held-out parquets weren't built (no RUN_HELDOUT_SAMPLES=1) or no previous model exists.

    Output

    • Console only — the per-regime delta table + verdict is printed to stdout / the pipeline log. Nothing is written to disk and nothing is folded into model_report.html.

Why ExpansionHunter is not re-run on HG002 / CHM1_CHM13 with the new model JSON before Stage 3

After Stage 2 exports a fresh model, it is tempting to think EH must be re-run on the training samples with that new model JSON compiled in, so its output reflects the new corrections — before evaluating in Stage 3. It doesn't, for three reasons:

  • The GQ model is applied post-hoc, in Python. EH emits, per allele, the raw allele size (eh) and every quality-metric feature unconditionally — those fields do not depend on any GQ model. The model JSON only tells the deployed EH binary how to turn those already-emitted features into PredictedLengthCorrectionFactor / pOk. Stage 3 computes those same quantities itself (model.predict_lcf_json / predict_proba_json) from the cached features, so it never needs EH to produce them.
  • The features are model-independent. Re-running EH with a new model JSON would not change a single feature value the parquets already hold (it would only add the model's outputs into new JSON). Since the parquets already contain the model's inputs, the existing EH JSON serves any model version.
  • Determinism / no leakage. The model uses no locus-id feature, and its coverage feature, like every other feature, is a value EH writes to its JSON whether or not a model is loaded, so the same cached JSON is valid regardless of which model was trained; re-running EH would only add cost (a fresh multi-hour cloud EH run over the 5.65M-locus catalog per sample) with no change to the evaluation inputs.

EH would need re-running only to regenerate the raw *.json.gz after an ExpansionHunter-bw2 code change that alters the calls or features themselves — which dataset._check_freshness detects by comparing each JSON's stamped build commit against the local EH checkout.
