ExpansionHunter Genotype-Quality Model — Training & Evaluation Pipeline

Orchestrated end-to-end by train_model.sh. The genotype-quality (GQ) model corrects ExpansionHunter (EH) allele-size calls: for each allele it predicts a length-correction factor (LCF) and direction probabilities (pOk / pTooShort / pTooLong).

1. Step-by-step breakdown

  • Stage 1 — Data ingestion

    dataset.py (with eh_json.py, features.py)

    Downloads from GCS and assembles the labeled training tables. Only two remote sources per sample are fetched now — the EH JSON and the tool-independent truth-genotypes TSV; the old precomputed *.for_comparison.*.alleles.tsv.gz table is no longer downloaded or read (its contents are reconstructed downstream from these two). Downloads are idempotent and freshness-aware: a local copy is re-used only while it is current — _check_freshness re-downloads (overwrites) any file whose bucket object is newer by last-modified time or whose md5 has changed, and the per-combo parquet is rebuilt whenever a source it derives from is newer than it.

    Inputs

    • gs://str-truth-set-v2/tool_results/<sample>/illumina/EHv5-bw2-optimized/<cov>_coverage/json/*.json.gz — raw EH output (tool EHv5-bw2-optimized = the bw2 fork's optimized-streaming build), one set per (sample, coverage) training combo: HG002 10x / 20x / 31x and CHM1_CHM13 46x. (Held-out samples use the same layout with a combined_catalog_43_samples_1.6M_loci/ subdir before json/.) Carries the genotype calls, confidence intervals, read-support counts, and per-allele quality metrics. These paths match the current ~/code/str-truth-set-v2 pipeline output layout (run_genotyping_tools.py DEFAULT_OUTPUT_DIR + {sample}/{data_type}/{tool}/{cov}_coverage/[subdir/]). Why: this is the sole source of the model's input features and the eh call being corrected — every feature the model reads comes from the JSON, never from a precomputed TSV, so features are computed identically across samples/coverages/branches.
    • gs://str-truth-set-v2/filter_vcf_v2/<sample>/<sample>.tandem_repeat_genotypes.tsv.gz — the tool-independent truth catalog (Short/Long allele repeat counts, NumRepeatsInReference, motif, per-allele purity) built from the dipcall/long-read-assembly pipeline; one file per sample (truth doesn't depend on short-read coverage). This is the same plain filter_vcf_v2 the genotyping pipeline reads its catalog from, so it stays consistent with the JSON (the dated filter_vcf_v2__… variants would not). Why: supplies the training target — the true allele size each call is scored against (t = log(eh) − log(true)) — and, being tied to no EH run, cannot go stale relative to one. It is filtered at load to EH's catalog loci (primary contigs + variant, non-hom-ref, per convert_truth_set_to_variant_catalogs.py) so it lines up with the loci the JSON actually contains.
    • 50 PROMOTED_HELDOUT_SAMPLES per-sample parquets (54 training sources with the 4 combos), built on demand via heldout.build_sample from the same two GCS sources and symlinked into the training pool. Why: HG002+CHM1_CHM13 alone leave the large-allele tail overfit to two genomes; these add ancestry/sex diversity at large sizes.

    Role

    • eh_json.extract_rows flattens each JSON into one row per allele. A no-call locus (EH emitted ./.) now yields rows with a null eh so the report can later count those truth alleles as "No Call"; these rows are dropped before training.
    • _load_truth_from_genotypes_tsv filters the truth catalog to EH's catalog loci (primary contigs + variant, non-hom-ref), then _join_truth left-joins it on (locus_id, allele_rank); _assert_catalog_agreement warns if the JSON and filtered-truth catalogs still disagree beyond tolerance (expected residual: stale training JSONs, and the held-out superset catalog).
    • label_and_filter drops chrM/unknown-contig, negative-control, missing/non-positive-eh-or-true (including the no-call rows), and missing-motif rows, then features.add_labels computes the targets and routes each allele to a genotyping regime.
    • assemble_branch splits rows by genotyping_branch (QuickGenotype fast-path vs full-genotyper fallback) and concatenates all combos + promoted samples per branch.

    Outputs

    • data/parquet/quick.parquet, data/parquet/full.parquet — labeled per-allele rows (features + t, dir_code, genotyping_regime), split by genotyper branch.
    • Per-combo parquets under data/real_quick/ (e.g. HG002_31x.parquet) — the pre-filter join, kept with locus_id/true/no-call rows so Stage 3's accuracy-by-size can reconstruct the tool-vs-truth comparison table.

    Note — what is not a Stage-1 (training) input: HG002 exome (3x) is not ingested here and never trains the model; it is only a Stage-3 report evaluation dataset (a legacy hand-built parquet). CHM1_CHM13 is a training combo (46x). Neither the exome data nor the 30 fully-held-out HPRC samples enter the training pool.

  • Stage 2 — Train + export

    train.py (with model.py)

    Inputs

    • data/parquet/quick.parquet, data/parquet/full.parquet — the labeled per-allele training rows from Stage 1. Why: these are the only fit inputs — each of the 3 genotyping-regime experts reads its branch's parquet, restricted to its own regime's rows, to fit both heads.

    Freshness guard: both train.py and report.py call dataset.assert_parquets_up_to_date before reading the pool, and exit with a rebuild message if a parquet is missing or older than any upstream JSON/TSV it derives from — so a stale parquet can never be silently trained/reported on.

    Role

    • For each regime (quick, full_spanning, full_nonspanning): hold out ~10% of chromosomes (seeded) as a chromosome-clean calibration set, cap training rows (seeded subsample).
    • train_q_median fits a quantile (median) regressor on t = log(eh) − log(true); train_direction fits a 3-class classifier + per-class isotonic calibration. Both use manual warm-start early stopping scored on the calibration set.
    • serialize_genotyping_regime exports trees/baseline/calibrators to the C++-compatible schema; verify_genotyping_regime re-implements inference from that serialized dict and asserts it reproduces sklearn's predictions.

    Outputs

    • model/genotype_quality_model_from_HG002_and_CHM1_CHM13.<date>.json.gz — gzipped JSON (format_version: 2): per-regime q-median trees + direction trees/calibrators + the feature_names contract. This is the exact file the ExpansionHunter C++ compiles in.
  • Stage 3 — Evaluate + report

    report.py (with metrics.py, accuracy_by_size.py, gen_datasets.py)

    Inputs

    • data/parquet/{quick,full}.parquet — the same training pool. Why: the deployed model is fit on all data and has no held-out set of its own, so honest accuracy is measured by re-fitting each regime out-of-fold under 5-fold chromosome-clean CV on this pool.
    • the exported model/*.json.gz (via --model). Why: it is applied unchanged (no re-fit) to compute LCF/pOk for the accuracy-by-size panels and the held-out section; it also labels the report header.
    • per-combo / per-sample parquets (from Stage 1, and Stage 4 for held-out). Why: accuracy_by_size.categorize_parquet rebuilds the str-truth-set "for_comparison" tool-vs-truth table directly from these — EH calls from the JSON-derived eh, truth from the joined true/num_repeats_in_reference, and "No Call" from the no-call rows — so no precomputed comparison TSV is needed.

    Role

    1. 3a. Homopolymer CV pass (--homopolymer-cv, run first): 5-fold chromosome-clean OOF on 1 bp-motif loci only → results_homopolymer.json, dir_oof_homopolymer.npz.
    2. 3b. Main CV + render: identical OOF on non-homopolymer rows; metrics.py scores q-head accuracy, direction log-loss/AUC/calibration, and the gated MAE (apply LCF only where pOk < 0.5); permutation importance + add-one ablation; renders the PNGs and report/model_report.html.
      Held-out regeneration (new, default-on): before rendering the dataset sections, report.py calls gen_datasets.generate("heldout_hprc", …) to refresh the held-out HPRC eval/stacked artifacts from any locally-built held-out parquets (no download). Pass --skip-heldout-samples to opt out; it is a no-op if those parquets haven't been built.

    Outputs

    • report/results.json, report/dir_oof.npz, the PNG charts, and the final report/model_report.html.
  • Stage 4 — External validationoptional · RUN_HELDOUT_SAMPLES=1

    Builds the 81 truly held-out sample parquets so Stage 3 can score them (the model is applied unchanged — the realistic "train on some samples, deploy on new samples" test). A ~7–8 GB download for the original 30 samples (roughly 3x that for all 81), off by default.

    1. 4a. heldout.py --build-only
      Input: GCS EH JSON + truth-genotypes TSV for the 81 held-out samples. Why: same two sources / same extract-join-label pipeline as Stage 1, so the held-out parquets carry identical features (and no-call rows) — a prerequisite for applying the frozen model to them.
      Output: data_eval_43/real_43/<SAMPLE>.parquet × 81.
    2. 4b. Fold into the report
      Once the parquets exist, the ordinary Stage-3 report.py run regenerates the held-out artifacts (report/eval_heldout_hprc.json, report/stacked_heldout_hprc.json) and renders the "held-out HPRC" section by default — no separate gen_datasets.py invocation is needed.
  • Stage 5 — New-vs-previous comparisonpost-hoc · stdout only · non-fatal

    compare_models.py (with heldout.py, gen_datasets.py)

    Applies the freshly-exported model and a previous model to the same held-out HPRC parquets and prints per-regime metric deltas + an overall verdict — the "should we ship the new one?" check. Both models are applied unchanged (no re-fit) to identical rows (same per-sample allele cap + seed as the report's held-out section, so the new model's numbers match it). Runs at the end of every train_model.sh; never fails the pipeline.

    Inputs

    • the new model (--new-model = Stage 2's export) and a previous model (--prev-model): defaults to whichever model is deployed in the local ExpansionHunter-bw2 checkout (ehunter/data/genotype_quality_model_*.json.gz), falling back to the most recent other model/*.json.gz in this repo.
    • the 81 held-out HPRC per-sample parquets from Stage 4 (data_eval_43/real_43/<SAMPLE>.parquet). Why: in neither model's training pool, so applying both to them is a fair generalization comparison.

    Role

    • Reuses heldout.run_eval for each model, then per regime compares gated MAE, distance reduction, pOk accuracy, median |err|, and net-helped (pOk<0.5) count, tallying metric wins into a NEW / PREVIOUS / MIXED verdict.
    • Self-skips (prints a note, exit 0) if the held-out parquets weren't built (no RUN_HELDOUT_SAMPLES=1), if no previous model exists, or if the two models have a different feature_names contract (comparison would be invalid).

    Output

    • Console only — the per-regime delta table + verdict is printed to stdout / the pipeline log. Nothing is written to disk and nothing is folded into model_report.html.

Why ExpansionHunter is not re-run on HG002 / CHM1_CHM13 with the new model JSON before Stage 3

After Stage 2 exports a fresh model, it is tempting to think EH must be re-run on the training samples with that new model JSON compiled in, so its output reflects the new corrections — before evaluating in Stage 3. It doesn't, for three reasons:

  • The GQ model is applied post-hoc, in Python. EH emits, per allele, the raw allele size (eh) and every quality-metric feature unconditionally — those fields do not depend on any GQ model. The model JSON only tells the deployed EH binary how to turn those already-emitted features into PredictedLengthCorrectionFactor / pOk. Stage 3 computes those same quantities itself (model.predict_lcf_json / predict_proba_json) from the cached features, so it never needs EH to produce them.
  • The features are model-independent. Re-running EH with a new model JSON would not change a single feature value the parquets already hold (it would only add the model's outputs into new JSON). Since the parquets already contain the model's inputs, the existing EH JSON serves any model version.
  • Determinism / no leakage. The model uses no locus-id feature, and its coverage feature, like every other feature, is a value EH writes to its JSON whether or not a model is loaded, so the same cached JSON is valid regardless of which model was trained; re-running EH would only add cost (and a fresh several-hour EH run over ~1.6M loci × 4 combos) with no change to the evaluation inputs.

EH would need re-running only to regenerate the raw *.json.gz after an ExpansionHunter-bw2 code change that alters the calls or features themselves — which dataset._check_freshness detects by comparing each JSON's stamped build commit against the local EH checkout.
